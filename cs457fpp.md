# Assignment Goal
The goal of this assignment is to document your initial decisions on what software system to build, any necessary supporting technologies, and the database and program design. A design document should provide enough detail about the project for someone with at least an equivalent skill-level to be able to create it themselves.

# Project Requirements

## System Requirements
1. There must be some information going into the system which persists in the database.  
2. There must be some information coming out of the system which is generated by the database.  
3. There must be a UI (which can fulfil the requirements listed above). 
	1. There is no requirement around how the UI should be implemented; GUIs, web apps, CLIs, etc. are all acceptable.  

## Software Requirements  
1. Any code that is not SQL should be written in Python3.  
	1. You must use either a Python3 library or framework to interact with the database.
2. Any code that is not SQL should use an Object-Oriented approach.  
3. Interactions between the database and outside of the system must pass through the software layer. 
	1. This requirement applies to while the system is running. If your outside data source is used to “seed” the database with information, that import can happen outside of the software layer.  

## Database Requirements  
1. The database management system must be PostgreSQL.  
2. There must be at least one “outside” data source (not generated within the software system). 
	1. The software system can have functionality to save data from the “outside” data source to the database.  
3. There must be at least 5 tables in the database’s schema which are involved in the system’s processes. 
	1. The system must at least be complex enough to meaningfully incorporate 5 or more tables into achieving its overall goal.  
4. Each table should in 3NF (third normal form).  
5. If a supplemental key is used, there must be an additional uniqueness constraint which enforces the actual primary key. 
	1. Natural keys are acceptable as primary keys. 
	2. Composite keys are acceptable as primary keys.

# Assignment Requirements

## 1. Outline the Overall Goal of Your Software System
This section has been split into functionality goals (i.e., what the software system shall be capable of by the submission deadline) and end-user goals (i.e., what the software system shall be used for and by whom) as the CS457 instructions left this distinction ambiguous.

Note: Not all of these goals will be met by the submission deadline as this document is tailored to fit a commissioned project whose scope exceeds the expected scope of this class.

###  Functionality Goal
This software system shall be able to dynamically generate Geographic Information System (GIS) figures (i.e., charts, graphs, maps) of smoke and wildfire coverage over lakes and cities in North America (NA), (https://en.wikipedia.org/wiki/List_of_sovereign_states_and_dependent_territories_in_North_America) over the years 2005 - 2025, specified by user input through a Graphical User Interface (GUI). 

CS457: User input shall be through a Command Line Interface (CLI).

### End-user Goal
This software system shall offer a set of figure generation tools to the UNR Wildfire Technology and Research Lab (WFTRL) (i.e., Dr. Facundo Scordo et al.) intended to replace/supplement the currently-in-use ad hoc generation process. End-users shall be able to access a web-application (web-application chosen over distributed software to eliminate OS-specific development costs and OIT requirements for distributed software) supported by a remotely hosted database.

CS457: End-users shall be able to download, install, and run distributed software on Unix-like systems supported by a locally hosted database.

## 3. Describe the Intended Infrastructure
This project shall be remotely hosted for database security at the expense of evaluation clarity. The client shall be able to request the web page and client (Vue, Tailwind, DaisyUI) through a reverse proxy (NGINX). On interaction, HTTP requests shall be passed to the WSGI HTTP server (Gunicorn) to be interpreted by the API (DRF). The API shall query the database (PostgreSQL) on behalf of the client. Database responses shall be processed by a set of R scripts for GIS figure generation. Figures shall be returned to the web client to be rendered. Infrastructure shall be setup once and maintained.

`hms_fires` and `hms_smokes` has been split horizontally by year (2003(5) - 2025) to optimise SQL performance. `lakes` has been split vertically by geometry (points, polys) to optimise SQL performance. `populated_places` has not been split. All tables have been indexed using `(gist) geometry`. `spatial_ref_sys` is a supplementary table to support PostGIS operations. Indices shall be used as primary keys for `hms_fires`, `hms_smokes`, `lakes`, and `populated_places`. `spatial_ref_sys` has the following keys:

